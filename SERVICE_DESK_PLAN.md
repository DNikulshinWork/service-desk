
## Общие правила работы над спринтом
1. В ответе предоставляйте только код, который нужно создать или изменить, с указанием пути к файлу.
2. Код должен быть строго типизирован, использовать Zod-схемы из `packages/shared` для валидации входных данных.
3. Каждый маршрут Fastify должен иметь полное описание `schema` (body, params, query, response) для автоматической генерации Swagger.
4. Обработка ошибок — через класс `AppError` (из `apps/api/src/errors.ts`) и централизованный errorHandler.
5. Все новые функции должны быть покрыты тестами: unit (чистая логика) и integration (с использованием `app.inject()` для Fastify).
6. Для фронтенда используйте Next.js App Router, Tailwind и shadcn/ui компоненты.
7. Не забывайте про безопасность: хеширование паролей (bcrypt), CSRF, httpOnly куки, rate limiting.
8. В конце каждого спринта убедитесь, что тесты проходят (`pnpm test`).

## Спринт 1 — Аутентификация, пользователи и компании
**Цель**: Полноценная регистрация/вход с JWT + OAuth2, управление профилем и организациями.

**Задачи**:
1. Реализовать регистрацию пользователя (`POST /api/v1/auth/register`): валидация email/password/name, хеширование пароля bcrypt, сохранение в БД.
2. Реализовать вход (`POST /api/v1/auth/login`): проверка email/password, выпуск access token (JWT с sub и role) и refresh token (сохранить в БД, установить httpOnly cookie).
3. Реализовать обновление токенов (`POST /api/v1/auth/refresh`): проверка refresh token из куки, выдача новой пары, ротация.
4. Реализовать выход (`POST /api/v1/auth/logout`): удаление refresh token из БД, очистка куки.
5. Добавить middleware `authenticate` для проверки access token из заголовка Authorization.
6. Добавить middleware `requireRole` для RBAC.
7. Создать OAuth2 endpoints: `GET /api/v1/auth/oauth/:provider` (редирект) и callback. Поддержка минимум GitHub и Google.
8. Реализовать профиль: `GET /api/v1/users/me`, `PATCH /api/v1/users/me`.
9. CRUD компаний: `POST /api/v1/companies`, `GET /api/v1/companies`, `GET /api/v1/companies/:id/users`.
10. Написать integration-тесты на все эндпоинты (включая сценарии с ролями).
11. На фронтенде: страницы логина, регистрации, профиля; компоненты форм с shadcn/ui.

**Ожидаемый результат**: полностью работающая аутентификация, авторизация и управление пользователями/компаниями. Все тесты зеленые.

## Спринт 2 — Управление заявками и комментарии
**Цель**: CRUD заявок с кастомными полями (JSONB), вложениями, комментариями, назначением.

**Задачи**:
1. Доработать `POST /api/v1/tickets`: создание заявки (subject, description, priority, customFields), автоматически записывать creatorId из токена.
2. `GET /api/v1/tickets`: список с фильтрацией (status, priority, assigneeId, search по subject), пагинацией, сортировкой. Учитывать роли: клиент видит только свои, агент — свои и неназначенные.
3. `GET /api/v1/tickets/:id` с включением комментариев и вложений.
4. `PATCH /api/v1/tickets/:id`: обновление полей, эскалация, назначение (`assigneeId`). Проверка прав.
5. Добавить комментарии: `POST /api/v1/tickets/:id/comments`, `GET /api/v1/tickets/:id/comments`.
6. Загрузка вложений через `@fastify/multipart`: `POST /api/v1/tickets/:id/attachments` (сохранение в MinIO, запись в БД), `GET /api/v1/attachments/:id/download` (pre-signed URL).
7. Интеграция с Elasticsearch: при создании/обновлении заявки ставить задачу в очередь BullMQ для индексации.
8. Unit-тесты логики прав доступа. Integration-тесты всех маршрутов с разными ролями.
9. Фронтенд: страницы списка заявок, детали, создание/редактирование; компонент комментариев и загрузки файлов.

**Ожидаемый результат**: полнофункциональное ядро системы тикетов, файлы хранятся в MinIO, поиск индексируется асинхронно.

10. Фронтенд: публичный портал базы знаний с поиском, админка для редакторов.

**Ожидаемый результат**: база знаний работает, поиск релевантный.

## Спринт 4 — SLA, рабочие календари и уведомления
**Цель**: Управление SLA-политиками, расчет дедлайнов с учетом календарей, эскалации, email/webhook уведомления.

**Задачи**:
1. CRUD SLA-политик: `POST /api/v1/sla/policies`, `GET /api/v1/sla/policies`.
2. CRUD рабочих календарей: `POST /api/v1/sla/calendars`, `GET /api/v1/sla/calendars`. Поддержка нескольких временных зон, настраиваемых рабочих дней, интервалов, праздников.
3. Сервис расчета дедлайнов (sla-calculator.ts): чистая функция, принимающая дату старта, календарь и время реакции/разрешения, возвращающая deadline с учетом рабочих интервалов и исключений. Покрыть 50+ юнит-тестов (переходы через выходные, праздники, смену часового пояса).
4. `GET /api/v1/tickets/:id/sla-status` — показывает текущий статус SLA по заявке (оставшееся время, просрочена ли).
5. При изменении статуса заявки автоматически применять SLA-политики и ставить задания в BullMQ на проверку дедлайнов.
6. Реализовать отложенные задания: напоминание за 30 минут до дедлайна, эскалация при просрочке (смена assignee/приоритета).
7. Email-уведомления (использовать nodemailer или заглушку для тестов): `POST /api/v1/notifications/send`.
8. Настроить webhooks: регистрация (`POST /api/v1/webhooks`), список, история доставок, ретраи.
9. Интеграция с мониторингом: `POST /api/v1/incidents/from-monitoring` — принимать алерты от Zabbix/Grafana и создавать заявки.
10. Тесты: unit для sla-calculator, integration для эндпоинтов SLA, вебхуков.
11. Фронтенд: настройки SLA и календарей, отображение SLA-статуса в деталях заявки.

**Ожидаемый результат**: SLA работает точно и надежно, уведомления доставляются, вебхуки отказоустойчивы.
